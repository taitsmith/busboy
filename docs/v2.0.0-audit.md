# Busboy 2.0.0 — Pre-Release Audit & Prioritized Issue List

## Context

Version 2.0.0 is the release that adds the app's headline feature: runtime switching between
two transit agencies (AC Transit and Chicago CTA). The codebase has also drifted somewhat stale
around it. This document is an **in-depth audit** producing a single, priority-ordered list of
issues to address before shipping 2.0.0 — bugs, technical debt, and quality-of-life gaps.

The audit was produced by four parallel read-only passes (multi-agency correctness, crash/error
handling, build/release readiness, tests/code-quality). **Every P0 and P1 item below was
personally re-verified against the source** (marked ✓); lower tiers are agent-reported and the
agents were accurate on everything spot-checked.

### Important: CLAUDE.md is stale — do not chase phantoms
Verified against `app/build.gradle`: the dependency "warts" CLAUDE.md lists are already fixed —
Hilt is **2.58** everywhere (not 2.55 vs 2.46.1), navigation is a single **2.9.8** (not

`versionName` is already **2.0.0** / `versionCode 27`. `gradlew`/`.gitignore` are now tracked. The
documented `NearbyViewModel._enableSearchButton` one-way-latch bug is **fixed**. CLAUDE.md itself

## P0 — Release blockers (fix before 2.0.0)

Hard crashes reachable in ordinary use, plus signing/keystore risk.

**1. Signing keystore `bbks.jks` is not gitignored — Critical (security, irreversible) ✓**
`.gitignore` (repo root) ignores *only* `secrets.properties`; `bbks.jks` is untracked-but-not-ignored,
one `git add -A` away from being committed. Committing the upload/signing key permanently
compromises the app's signing identity (it stays in git history forever). `local.properties`,
`/build`, `.idea/`, and the 13 MB `app/release/*.aab` are likewise unignored.
→ Replace `.gitignore` with a standard Android one: `*.jks`, `*.keystore`, `local.properties`,
`/build`, `.gradle`, `.idea`, `/app/release`, `*.aab`, `.kotlin`, plus the existing
`secrets.properties`. Do this **first**, before any release-time `git add`.

**2. Release build is signed with the debug key — Critical (release config) ✓**
`app/build.gradle:23` sets `signingConfig signingConfigs.debug` in `defaultConfig`; the
`release {}` block (`:36-41`) declares no `signingConfig`, and there is no `signingConfigs.release`
anywhere. `./gradlew bundleRelease` therefore produces a **debug-signed** artifact. The shippable
AAB in `app/release/` only exists because it was built via Android Studio's signing wizard — the
release is **not reproducible from the repo** and no CLI/CI release build is possible.
→ Add `signingConfigs.release` reading store/key credentials from a gitignored `keystore.properties`
or env vars (never hardcoded), and set `release { signingConfig signingConfigs.release }`.

**3. Empty prediction list crashes the predictions collector — Critical (crash) ✓**
`ByIdViewModel.kt:69` does `p[0].stpnm` inside `.collect`. `ApiRepositoryImpl.stopPredictions`
emits `Success` with an **empty** list whenever `prd` is empty, or every prediction is removed by
the `dyn != 0` filter (`ApiRepositoryImpl.kt:30`) — both routine (a stop with no active/stopping
buses). The `.catch` at `:62` only catches *upstream* errors, not exceptions thrown inside
`collect`, so this `IndexOutOfBoundsException` escapes to `viewModelScope` → process crash.
→ `p.firstOrNull()`; route empty to a "no predictions" status instead of indexing.

**4. `getAlerts()` uncaught exception crashes after every successful prediction — Critical (crash) ✓**
`ByIdViewModel.kt:80-87` collects `serviceAlerts(...)` with no `.catch`. That flow throws
`"404"/"CALL_FAILURE"/"UNKNOWN"` on any failure (AC alerts endpoint or CTA `getdetours`), and
`getAlerts()` runs automatically on every prediction success (`:73`). A routine transient alerts
failure → uncaught throw in `viewModelScope.launch` → crash. (`stopId.value!!` at `:82` is a second
edge — `postValue` at `:59` is async and may not have landed yet.)
→ Add `.catch { }` (alerts are best-effort); pass the id in rather than reading `stopId.value!!`.

**5. Adding a favorite (AC Transit) can crash — High (crash) ✓**
`ByIdViewModel.addStopToFavorites` (`:112-123`) collects `getLinesServedByStops(...)` with no
error handling. For AC Transit that's a per-stop network call that throws on failure; uncaught in
`viewModelScope.launch(IO)` → crash. (CTA reads the local catalog, so CTA is safe.)
→ Wrap in `.catch`, forward to `statusRepository`.

**6. Bus-details long-press can crash on empty/failed vehicle — High (crash) ✓**
`ByIdViewModel.getBusDetails` (`:89-94`) has no try/catch. AC's `getDetailedBusInfo` does
`getDetailedVehicleInfo(vid)[0]` (throws on empty); CTA throws `NULL_BUS_COORDS`/`404`. Either
propagates uncaught out of `viewModelScope.launch(IO)` → crash.
→ Wrap in `try/catch`, emit `BusState.Error` on failure.

**7. Loading spinner never cleared on error → permanent UI hang — High ✓**
`getBusLocation` (`ByIdViewModel.kt:96-110`) calls `isLoading(true)` but never `isLoading(false)`;
the happy path is cleared only by the waypoints observer, and the error path sets `BusState.Error`
into a collector whose arms are empty (`ByIdFragment.kt:75`, `MapsFragment.kt:137`). `getWaypoints`
(`:125-137`) only handles `"empty_response"` and just `printStackTrace()`s everything else. Result:
a failed vehicle-location or waypoint call leaves `navHostFragment` INVISIBLE with the progress bar
spinning forever, no recovery.
→ Clear loading in the error branches and emit a status code; give the `BusState.Error` arm real
handling (also fixes item 15).

**8. `MapsFragment.onDestroy()` crashes on uninitialized `googleMap` — High (crash, known)**
`MapsFragment.kt:177-182` calls `googleMap.clear()` / listener-nulling on the `lateinit var
googleMap`, assigned only inside the async `OnMapReadyCallback`. Destroy the fragment before the
map loads (navigate in and straight back out, or `findFragmentById(R.id.map)` returns null) →
`UninitializedPropertyAccessException`. Documented in CLAUDE.md; still present.
→ Guard every use with `if (::googleMap.isInitialized)`.

## P1 — Headline-feature correctness (strongly recommended before 2.0.0)

These don't crash, but they undermine the flagship agency-switch or its polish.

**9. Agency switch leaves the *previous* agency's data on screen — High ✓**
`MainActivity.onAgencyChanged` (`:99-111`) only navigates + shows a snackbar; it never resets the
Activity-scoped `ByIdViewModel`/`NearbyViewModel`, whose `StateFlow`s still hold the last agency's
`Success` results. The freshly-created fragment re-collects and immediately re-renders **stale**
AC-Transit predictions/nearby-stops after switching to CTA (and vice-versa). The in-code comment
("resets the app to a clean By-ID screen") is inaccurate.
→ Call `byIdViewModel.reset()` / `nearbyViewModel.reset()` from `onAgencyChanged`.

**10. Prediction/vehicle polling loops are never cancelled — High ✓**
`getPredictions`/`getBusLocation` launch infinite `while(true){emit; delay(60s)}` flows with no
`Job` tracking and no cancellation of the prior launch. Every search/tap starts another permanent
poller. `DelegatingRemoteDataSource.active()` is read once per collection, so a loop begun under AC
Transit polls AC forever — after a switch to CTA the old loop and new loop both write
`_predictions`, so the list **flip-flops between agencies ~every 60s**, and battery/network cost
grows per search.
→ Keep a `Job` per stream, `cancel()` before relaunch (or `flatMapLatest`); cancel on `reset()`.

**11. CTA "no service" shows a generic "unknown error" — Medium ✓**
`ApiRepositoryImpl.kt:23` maps to the friendly `NO_SERVICE_SCHEDULED` only when the API msg equals
AC Transit's exact `"No service scheduled"`. CTA's BusTracker uses different phrasing ("No arrival
times found" / "No data found"), so a CTA stop with no buses falls to `throw Exception("UNKNOWN")`
→ user sees "unknown error" instead of the intended no-service message.
→ Match CTA's no-data messages too (case-insensitive substring), or key off a normalized condition.

**12. Cold-start race fires a spurious "Now showing CTA" switch — Medium ✓**
`MainActivity.kt:79` collects `selectedAgencyState.drop(1)`. `selectedAgencyState` is
`stateIn(Eagerly, AC_TRANSIT)`, so its first value is the seed until DataStore's async read
resolves. If the collector subscribes before the read completes, `drop(1)` discards the seed and
then treats the stored `CTA` as a "change" → spurious agency-switched snackbar + nav reset on
launch, for any user whose stored agency ≠ default. Nondeterministic.
→ Gate on a first-real-emission flag / drop-until-distinct rather than positional `drop(1)`.

**13. CTA screens still show AC-Transit copy & imagery — Medium (QoL, "most visible")**
The By-ID hint is `"ex 56669"` (`strings.xml:6`) even under CTA (CTA ids are ~4 digits), and the
large placeholder image + its screen-reader description are hard-coded to an AC Transit bus flag
(`fragment_by_id.xml:50-60`, `ic_busflag`, `accessibility_busflag_img_desc` = "AC Transit bus
flag"). This is the most visible cross-agency inconsistency for a CTA-headline release.
→ Swap hint/image/content-description off `settingsRepository.selectedAgencyState`.

**14. CTA service alerts are unfiltered — every CTA stop shows all system-wide detours — Medium (QoL) ✓**
`CtaRemoteDataSource.serviceAlerts` (`:52-64`) discards `stpid` and calls `getDetours(null)`. A CTA
By-ID user gets "N service alerts" where N is every detour in the CTA system. Marked "Phase 3:
unfiltered" in-code, so arguably a known deferral — but noisy/misleading for the flagship feature.
→ Filter `dtrs` by the stop's routes (from the catalog's `linesServed`) before mapping, or defer
explicitly and document.

## P2 — Robustness & silent failures (nice to have for 2.0.0)

**15. Silent `BusState.Error -> {}` — no feedback on vehicle-lookup failure — Medium.**
`ByIdFragment.kt:75`, `MapsFragment.kt:137`. Most visible for CTA (`NULL_BUS_COORDS` when a bus
just went out of service). Fixed together with item 7.

**16. `StatusRepository` uses a conflating `StateFlow` as a one-shot event bus — Medium.**
`di/StatusRepository.kt`. `StateFlow` de-dupes equal values, so two identical consecutive codes
fire the snackbar once, and a rapid `Loading→StatusUpdate→Success` can conflate the status away
before the Main collector sees it → errors silently show nothing. → Use a `SharedFlow`/`Channel`
(replay 0) for one-shot events, keep `LoadingState` separate.

**17. AC data source `[0]` on possibly-empty lists — Low.**
`AcTransitRemoteDataSource.kt:106` (`getDetailedVehicleInfo(vid)[0]`) and `:119`
(`patterns?.get(0)`) throw on empty, while `CtaRemoteDataSource` uses `firstOrNull`/empty-guards
throughout. Uneven crash-safety across the shared interface. → Mirror CTA's guards.

**18. Empty walking-directions polyline crashes the map — Medium.**
`getDirectionsToStop` returns an empty list (doesn't throw) when the Maps response has no steps;
`MapsFragment.setupForRouteDisplay` then indexes `polylineCoords[0]` → `IndexOutOfBounds`. → Treat
empty as `DIRECTION_FAILURE` before navigating; guard the index. (`CtaRemoteDataSource.kt:147`
`routeList?.get(0)` also throws on a non-null empty list.)

**19. `response.prd!!` / `exception.message!!` NPE edges — Low.**
`ApiRepositoryImpl.kt:29` (`prd!!` when a payload has neither `prd` nor `error`), `ByIdFragment.kt:64`
(`exception.message!!`). Caught by `.catch` so no hard crash, but surfaces as a non-actionable
error. → `prd.orEmpty()`, `message ?: "UNKNOWN"`.

**20. `NumberFormatException` on oversized distance input — Low.**
`NearbyFragment.kt:168` `s.toInt()` on the distance field (numeric but unbounded) overflows Int for
11+ digits → crash. (The By-ID field is capped at 5 digits.) → `toIntOrNull()` + range check or
`android:maxLength`.

**21. Dead status-code arms + one dropped code — Low.**
`MainActivity.updateStatus` (`:113-135`) has arms for `NULL_PRED_RESPONSE`, `NO_FAVORITE_STOPS`,
`HELP_REQUESTED` that are never emitted; conversely `WAITING_ON_LOCATION`
(`NearbyViewModel.kt:124`) is emitted but has **no** arm, so "waiting on location" shows nothing.
Symptom of the informal string-code "enum" with no single source of truth. → Remove dead arms, add
the missing one (or adopt a sealed enum). *(Note: item 3's fix wires `NULL_PRED_RESPONSE` live, so
that arm is no longer dead.)*

**22. Location-permission grant is never observed — Medium (QoL).**
`MainActivity.kt:197` sets `NearbyViewModel.locationPermGranted = true`, but nothing observes it and
denial does nothing. After the system grant dialog the pending nearby search isn't retried and the
user gets no feedback. → Observe it (or migrate to the ActivityResult permission API) to re-invoke
the search; handle denial with a message.

## P3 — Test coverage gaps (recommended for a major release)

The multi-agency **routing spine + prediction transform are well tested**
(`ApiRepositoryTransformTest`, `AcTransit/CtaRemoteDataSourceTest`, `DelegatingRemoteDataSourceTest`,
`CtaStopCatalogTest`, `MigrationTest`). Gaps cluster at the new feature's **stateful/persistence
edges**:

**23. Agency-stamped favorites has no repository-level test — High (test-gap).**
The core 2.0 data guarantee (same numeric `stopId` not colliding across agencies) lives in
`DatabaseRepository.getAllStops`/`addStops`. `RoomTest` only hits `StopDao.getAll(agency)` directly.
→ JVM test with the existing `FakeSettingsRepository`: insert the same `stopId` under `AC_TRANSIT`
and `CTA`, assert reads are agency-scoped.

**24. `SettingsRepositoryImpl` is untested — Medium (test-gap).**
DataStore round-trip, default-to-`AC_TRANSIT`-when-unset, and `toAgency()` on an invalid stored
string are all uncovered. `toAgency` is trivially unit-testable even without DataStore.

**25. CTA catalog-backed Nearby & seeding untested — Medium (test-gap).**
`CtaRemoteDataSource.nearbyStops`/`linesServedByStop`, the `feetToMeters = 0.3048` conversion (a
real unit-bug risk — UI enters feet, catalog works in meters), and `CtaStopCatalog`'s Room-backed
methods/TSV seeding have no tests (only the pure companion helpers do). No androidTest for
`CtaCatalogDatabase`.

**26. `DelegatingRemoteDataSource`: 7 of 8 delegations untested — Low (test-gap).**
Only `predictions` routing is verified; a copy-paste routing error in the other seven would pass
CI. → Parameterize the existing test across the methods. *(Also: `RoomTest.deleteStops` /
`writeStopsDeleteAndRead` build a Flow they never collect — they assert nothing; and
`FakeLocationRepository.fakeLocation()` sets `latitude` twice and never `longitude` — item 40.)*

## Suggested remediation order

1. **Item 1 first** — extend `.gitignore` so the keystore can never be committed.
2. **Items 3–8** — the ViewModel crash cluster shares one root cause: wrap every `viewModelScope`
   flow collection in `.catch { → statusRepository }`, guard list indexing with `firstOrNull()`, and
   clear loading on error. Plus the `MapsFragment` `isInitialized` guard.
3. **Item 2** — add the release signing config (needed for a reproducible/CI 2.0.0 build).
4. **Items 9–14** — headline-feature correctness/polish.
5. **Items 15–22** — robustness/silent-failure hardening.
6. **Items 23–26** — lock in the new feature with persistence-edge tests.
7. **Items 27–40** — tech-debt cleanup, opportunistically.

## Work log

All P0 items fixed on branch `chore/2.0.0-audit`. `./gradlew testDebugUnitTest` passes (all unit
tests green, full module compiles) and `./gradlew :app:signingReport` confirms the new release
signing config resolves. No commits made (staging via `git add` only); in-progress CTA feature
changes left untouched.

**Item 1 — .gitignore.** Rewrote the near-empty `.gitignore` to a standard Android one: now ignores
`*.jks`/`*.keystore`, `keystore.properties`, `local.properties`, `/build`, `/app/build`, `.gradle/`,
`*.aab`/`*.apk`, `/app/release`, `.idea/`. The signing keystore can no longer be committed.

**Item 2 — release signing.** Removed `signingConfig signingConfigs.debug` from `defaultConfig`
(`app/build.gradle`), added a `signingConfigs.release` that reads store/key credentials from a
gitignored `keystore.properties` (with a committed `keystore.properties.example` template documenting
the keys, incl. the existing `BUSBOY_K` alias), and set `release { signingConfig = ... }` to use it
when present, falling back to debug signing when absent so a fresh clone/CI still builds. **Action
still required by you:** `cp keystore.properties.example keystore.properties` and fill in the real
passwords to produce a shippable, reproducible release build.

**Items 3–7 — ByIdViewModel crash cluster.** `getPredictions` now guards the empty list with
`firstOrNull()` (empty → `NULL_PRED_RESPONSE` status instead of a `p[0]` crash) and clears loading in
`.catch`. `getAlerts` takes the id as a param (no more async `stopId.value!!`) and wraps the flow in
`.catch { }` (alerts are best-effort). `getBusDetails` is wrapped in try/catch → `BusState.Error`.
`getBusLocation` clears loading in `.catch`. `addStopToFavorites` wraps the flow in `.catch` →
status. `getWaypoints` now emits a status on *any* failure (not just `empty_response`), which clears
the spinner — fixing the permanent-hang path. `ByIdFragment`'s empty `BusState.Error` arm now
surfaces the error, and both fragment error arms use `message ?: "UNKNOWN"` (no `!!`).

**Item 8 — MapsFragment.onDestroy.** Guarded the `googleMap` teardown with `if (::googleMap.isInitialized)`.
